# Phase 2: HLD — Implementation Plan

**Goal:** Write the complete `kb/hld/` subject: the interview procedure, back-of-envelope estimation, 21 fundamentals pages, 6 distributed-systems pages, 25 case studies, a cheatsheet, and a practice page.

**Spec:** `docs/superpowers/specs/2026-10-14-software-engineering-kb-design.md` (sections 3.3, 4, 5.1, 5.3, 6, 7, 8, 9)

**Process (same as Phase 1):** a Sonnet drafter per assignment reads `docs/superpowers/drafting-brief.md` and its assignment in this plan. An Opus reviewer per finished draft reads `docs/superpowers/review-brief.md`. Opus (the main session) checks the reviewer's open claims, runs `tools/check-mermaid.sh` and the gate, and commits each assignment. Up to 5 drafters run at the same time.

## Common assignment text

Every assignment includes this paragraph:

> Read `docs/superpowers/drafting-brief.md` in full before you start. It is binding. Then read `kb/hld/README.md` for the subject's page list. HLD pages explain systems, so most of a page is text, tables, and Mermaid diagrams. Give numbers where numbers decide a design (latency, throughput, storage), each labeled "approximate" with a source. Name real systems as examples (for example Kafka, Cassandra, DynamoDB, Redis, PostgreSQL, Nginx, Envoy) and state each fact about them from its official documentation or its original paper. Where a Java example helps (a consistent-hashing ring, a token bucket, a Bloom filter), write a small runnable program with `main` first and its own imports.

Rules for links: the LLD pages exist (`kb/lld/...`). The HLD pages in your batch exist when the batch ends, so link to them. Every other planned page is a backticked path from spec section 3, with its exact file name.

## Batch 1: Fundamentals (`kb/hld/fundamentals/`)

Each page uses the topic template (drafting brief section 4.1).

### H1 — `01-scalability-and-availability.md` (P1), `02-load-balancing-dns-cdn.md` (P1)

`01`: vertical and horizontal scaling and when each ends; stateless services and where state goes (session store, sticky sessions and their cost); latency vs throughput, percentiles (p50, p99, p999) and why averages hide tail latency (cite Dean and Barroso, "The Tail at Scale", 2013); availability as a number of nines with the downtime per year table; serial and parallel availability math (worked example); SLA, SLO, SLI and error budgets (cite the Google SRE book); redundancy, failover, and single points of failure; Amdahl's law in brief.

`02`: L4 and L7 load balancers (what each sees and can do); algorithms (round robin, weighted, least connections, least response time, IP hash, consistent hashing, power of two random choices — cite Mitzenmacher); health checks (active and passive), connection draining; TLS termination; global load balancing with DNS (GeoDNS, anycast); DNS in system design (TTL trade-offs, caching layers — protocol details live in `kb/networking/06-dns.md`); CDNs (push vs pull, cache keys, invalidation, origin shield, edge compute); real products (Nginx, HAProxy, Envoy, AWS ALB/NLB) with their documented features only.

### H2 — `03-caching.md` (P1)

Cache placement (client, CDN, reverse proxy, application, distributed cache, database buffer pool); cache-aside, read-through, write-through, write-back, write-around, each with a sequence diagram and its consistency and failure behavior; TTL and eviction (LRU, LFU, link to `../../lld/case-studies/02-lru-and-lfu-cache/README.md`); invalidation strategies and the race between update and invalidation (delete-after-write and its stale-read window; cite the Facebook "Scaling Memcache at Facebook" NSDI 2013 paper, including leases); cache stampede and its fixes (locking, request coalescing, probabilistic early expiration — cite Vattani et al. "Optimal Probabilistic Cache Stampede Prevention"); hot keys (local caching, key replication); cache penetration (negative caching, Bloom filters); Redis vs Memcached (data types, persistence, threading model, from their docs); how to size a cache (working set, hit ratio math).

### H3 — `04-choosing-a-database.md` (P1), `05-replication.md` (P1)

`04`: a decision procedure from access patterns to a database family; relational (transactions, joins, constraints) vs key-value vs document vs wide-column vs graph vs time-series vs search, each with when to use and when not; a table of real systems per family; polyglot persistence and its cost; how to justify the choice in an interview. Internals link to `kb/databases/` pages by backticked path.

`05`: why replicate (availability, read scale, latency); leader-follower (synchronous, asynchronous, semi-synchronous), multi-leader, leaderless (Dynamo-style quorums, read repair, hinted handoff, anti-entropy); replication lag and its anomalies (read-your-writes, monotonic reads, consistent prefix) with the fixes; failover (detection, election, split brain, fencing); replication logs (statement-based, WAL shipping, logical/row-based); examples from PostgreSQL, MySQL, Cassandra, DynamoDB docs. Cite Kleppmann, *Designing Data-Intensive Applications*, chapter 5, and the Dynamo paper (DeCandia et al., SOSP 2007).

### H4 — `06-partitioning-and-sharding.md` (P1), `07-consistency-and-cap.md` (P1)

`06`: why partition; range vs hash partitioning (hot spots, range scans); consistent hashing with virtual nodes (runnable Java ring example; cite Karger et al. 1997); rendezvous hashing; rebalancing strategies (fixed partitions, dynamic splitting, proportional to nodes); secondary indexes (local vs global); request routing (client, proxy, coordination service); hot keys and celebrity problems; resharding without downtime; examples (Cassandra tokens, DynamoDB partitions, MongoDB chunks, Vitess) from docs.

`07`: the CAP theorem stated precisely (Gilbert and Lynch 2002 proof; what "consistency" and "availability" mean there; why "pick two" is misleading — cite Brewer 2012 "CAP Twelve Years Later"); PACELC (Abadi 2012); consistency models from strongest to weakest (linearizability, sequential, causal, read-your-writes, monotonic reads, eventual) with an example of each; quorums (N, R, W; R + W > N and what it does not guarantee); tunable consistency in Cassandra and DynamoDB; how to answer "is your system CP or AP" in an interview.

### H5 — `08-message-queues-and-streams.md` (P1)

Queues vs logs (RabbitMQ/SQS vs Kafka/Kinesis); delivery semantics (at-most-once, at-least-once, exactly-once and what Kafka's idempotent producer and transactions actually guarantee, from Kafka docs); ordering (per partition, per key; what breaks it); consumer groups and partition assignment; offsets and replay; backpressure; dead-letter queues and poison messages; retries with backoff; the transactional outbox pattern (link `../distributed-systems/03-distributed-transactions.md`); delay queues; fan-out patterns; retention and compaction; when to use a queue vs a stream vs direct calls. Link `../../lld/case-studies/15-pub-sub-message-queue/README.md` for the in-process design.

### H6 — `09-communication-patterns.md` (P1), `10-storage-types.md` (P2)

`09`: synchronous request-response (REST, gRPC) vs asynchronous (queues, events); real-time push: polling, long polling, Server-Sent Events, WebSocket — each with connection model, server cost, proxies and load balancers, reconnection; webhooks (delivery, retries, signatures); which to choose for which requirement (a decision table); connection scale numbers labeled approximate. Protocol details link `kb/networking/08-websockets-and-realtime.md`; API design details link `kb/api-design/` pages.

`10`: block, file, and object storage (interfaces, consistency, cost, use cases); object storage design (buckets, keys, multipart upload, presigned URLs, lifecycle tiers, S3 strong read-after-write consistency since December 2020 — cite the AWS announcement); blob metadata in a database plus blob in object storage; data lakes and formats (Parquet, ORC) in brief; erasure coding vs replication (storage overhead and repair cost).

### H7 — `11-search-and-indexing.md` (P2), `12-reliability-patterns.md` (P1)

`11`: the inverted index (tokenizing, normalization, posting lists); ranking basics (TF-IDF, BM25); Elasticsearch/OpenSearch architecture (index, shard, replica, segment, refresh and near-real-time search, from docs); indexing pipeline (change data capture into the index); search vs database queries; autocomplete basics (link the HLD autocomplete case study).

`12`: timeouts (how to set them from percentiles); retries (which errors to retry, idempotency requirement, retry budgets, retry storms); exponential backoff with jitter (cite the AWS Architecture Blog "Exponential Backoff And Jitter"); circuit breaker (states, thresholds; Resilience4j docs); bulkhead; rate limiting and load shedding (link `13-rate-limiting-algorithms.md`); graceful degradation and fallbacks; idempotency keys; health checks and readiness vs liveness; chaos testing in brief. Runnable Java circuit breaker with an injected clock.

### H8 — `13-rate-limiting-algorithms.md` (P1), `14-microservices-and-monoliths.md` (P1)

`13` (the home page for rate-limiting algorithms): token bucket, leaky bucket (as a queue and as a meter), fixed window, sliding log, sliding window counter — each with the algorithm, memory cost, burst behavior, accuracy, and a runnable Java implementation with an injected clock; comparison table; where to enforce (client, gateway, service); distributed rate limiting (central store, Redis with Lua scripts for atomicity, local plus global hybrid, cite Redis docs); response headers (`429`, `Retry-After`, the IETF RateLimit header draft — state its draft status); Cloudflare's sliding window counter measurement (0.003% in their blog). Link the LLD rate limiter case study.

`14`: monolith, modular monolith, microservices — trade-offs and when to choose each; service boundaries (business capabilities, bounded contexts); data ownership (database per service) and its consequences; API gateway; service discovery (client-side vs server-side; Consul, Kubernetes DNS); service mesh (sidecar, mTLS, retries; Istio/Linkerd docs); inter-service communication choices; distributed tracing need; migration with the strangler fig pattern (cite Fowler); common failure modes (distributed monolith, chatty services).

### H9 — `15-unique-id-generation.md` (P1), `16-event-driven-architecture.md` (P1)

`15`: requirements for IDs (uniqueness, ordering, size, coordination); UUID versions (v4 random, v7 time-ordered — cite RFC 9562, 2024); database auto-increment and its limits; ticket servers (Flickr); Snowflake layout (timestamp, worker id, sequence; cite Twitter's announcement) with a runnable Java generator and clock-skew handling; ULID; k-sortable IDs and index locality; collision probability math for random IDs.

`16` (the home page for event-driven architecture, CQRS, and event sourcing): events vs commands vs messages; event notification vs event-carried state transfer vs event sourcing (cite Fowler "What do you mean by Event-Driven?"); event sourcing (event store, projections, snapshots, schema evolution, when not to use it); CQRS (separate read and write models, eventual consistency, Fowler's warning); choreography vs orchestration for workflows (link sagas in `../distributed-systems/03-distributed-transactions.md`); change data capture (Debezium docs); event schema and versioning.

### H10 — `17-batch-and-stream-processing.md` (P2), `18-geospatial-indexing.md` (P2)

`17`: batch vs stream; MapReduce model (cite Dean and Ghemawat 2004); Spark (RDD/DataFrame, lazy evaluation, shuffles); stream processing (event time vs processing time, windows — tumbling, sliding, session — watermarks, late data; cite the Dataflow model paper, Akidau et al. 2015); Flink and Kafka Streams state and checkpoints (from docs); exactly-once in stream processing and what it means; Lambda vs Kappa architectures (cite Jay Kreps "Questioning the Lambda Architecture").

`18`: why spatial indexes; geohash (encoding, precision table, neighbor search, edge problems); quadtree (static and dynamic); S2 cells and H3 hexagons (from their docs); R-tree and PostGIS in brief; nearby search with a runnable Java geohash encoder; trade-offs table.

### H11 — `19-multi-region-and-disaster-recovery.md` (P2), `20-observability-in-design.md` (P2), `21-security-in-design.md` (P2)

`19`: why multi-region; active-passive vs active-active; data replication across regions and conflict handling (link CRDTs); RPO and RTO with worked examples; DR strategies (backup and restore, pilot light, warm standby, multi-site — cite the AWS DR whitepaper); failover and failback; data residency and its effect on design; latency-based routing.

`20`: what to measure in a design (the four golden signals — cite the Google SRE book; RED and USE in brief); where to put metrics, logs, traces in a design diagram; SLO-based alerting; capacity signals. Full observability practice lives in `kb/engineering-practice/08-observability.md` (backticked path).

`21`: authentication at the edge (API gateway, tokens), service-to-service auth (mTLS, workload identity), authorization placement, encryption in transit and at rest, key management (KMS, envelope encryption), secrets, rate limiting and DDoS protection, input validation at boundaries, audit logs. Depth on each topic lives in `kb/security/` pages (backticked paths).

## Batch 2: Distributed systems (`kb/hld/distributed-systems/`)

### D1 — `01-failures-and-time.md` (P2), `02-consensus-and-leader-election.md` (P1)

`01`: partial failures; network partitions and the fallacies of distributed computing (cite Deutsch); timeouts and failure detection (phi accrual — cite Hayashibara et al. 2004); clocks: wall-clock drift, NTP, monotonic clocks; Lamport clocks (cite Lamport 1978) and vector clocks with runnable Java examples; TrueTime in brief (cite the Spanner paper, 2012); hybrid logical clocks.

`02`: why consensus; FLP impossibility in one paragraph (cite Fischer, Lynch, Paterson 1985); Raft in detail (terms, leader election, log replication, commit index, safety rules, membership changes — cite Ongaro and Ousterhout 2014 and raft.github.io), with sequence diagrams; Paxos in brief (cite Lamport "Paxos Made Simple"); leader election built on consensus (ZooKeeper ephemeral sequential znodes, etcd leases — from docs); what consensus costs (latency, quorum size, odd node counts).

### D2 — `03-distributed-transactions.md` (P1), `04-probabilistic-data-structures.md` (P1)

`03`: why distributed transactions are hard; two-phase commit (protocol, blocking problem, coordinator failure); three-phase commit in brief; sagas (choreography vs orchestration, compensating actions — cite Garcia-Molina and Salem 1987); the transactional outbox and inbox patterns; idempotent consumers; exactly-once claims examined; when to avoid distributed transactions (design boundaries around one database). Link `../fundamentals/16-event-driven-architecture.md` and the LLD wallet and shopping-cart case studies.

`04`: Bloom filter (math for false-positive rate, optimal hash count, runnable Java); counting Bloom filter and cuckoo filter in brief; count-min sketch (runnable Java, error bounds — cite Cormode and Muthukrishnan 2005); HyperLogLog (idea, standard error ≈ 1.04/√m, Redis `PFADD`/`PFCOUNT` docs — cite Flajolet et al. 2007); Merkle trees for anti-entropy (Dynamo, Cassandra docs); gossip protocols (SWIM — cite Das et al. 2002); where each appears in system design interviews.

### D3 — `05-distributed-locks-and-leases.md` (P2), `06-crdts-and-conflict-resolution.md` (P2)

`05`: when you need a distributed lock (efficiency vs correctness); leases; fencing tokens (cite Kleppmann "How to do distributed locking", 2016); the Redlock algorithm (Redis docs) and the debate (Kleppmann's critique and Antirez's response — present both precisely); ZooKeeper and etcd locks; database-based locks (`SELECT ... FOR UPDATE`, advisory locks).

`06`: concurrent writes and conflicts; last-writer-wins and its data loss; version vectors; CRDTs (state-based vs operation-based; G-Counter, PN-Counter, OR-Set, LWW-Register — cite Shapiro et al. 2011) with runnable Java G-Counter and PN-Counter; operational transformation vs CRDTs for collaborative editing (cite the Jupiter paper and Kleppmann's work in brief); real systems (Riak, Redis Enterprise CRDTs, Automerge — from docs).
