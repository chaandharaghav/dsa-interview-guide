### SQL rules

## Batch 1: Relational core (`kb/databases/`)

Each page uses the topic template (drafting brief section 4.1).

### DB1 — `01-relational-model-and-sql.md` (P1)

The relational model (relation, tuple, attribute, domain, key, relational algebra: selection, projection, join, union, difference) and how SQL departs from it (bags, not sets; `NULL`). The logical order of query processing (`FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `DISTINCT`, `ORDER BY`, `LIMIT`) and its consequences (why `WHERE` cannot use a `SELECT` alias). `NULL` and three-valued logic (the `NOT IN` with a `NULL` trap, `IS DISTINCT FROM`, `COALESCE`). Joins: inner, left, right, full, cross, self join; semi-join and anti-join with `EXISTS` and `NOT EXISTS`; join conditions in `ON` against `WHERE` for outer joins. Grouping and aggregates (`COUNT(*)` against `COUNT(col)`, `HAVING` against `WHERE`, rows that a `GROUP BY` drops). Subqueries: scalar, correlated, `IN`, `EXISTS`, derived tables. CTEs and recursive CTEs (an org-chart hierarchy). Window functions: `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `NTILE`, `LAG`, `LEAD`, running totals, frames (`ROWS` against `RANGE`, the default frame and its surprise with `LAST_VALUE`), `PARTITION BY`. Set operations (`UNION` against `UNION ALL`, `INTERSECT`, `EXCEPT`). `CASE` and conditional aggregation. DML: `INSERT`, `UPDATE`, `DELETE`, upsert (`INSERT ... ON CONFLICT` in PostgreSQL and SQLite, `INSERT ... ON DUPLICATE KEY UPDATE` in MySQL, `MERGE`), `RETURNING`. Views and materialized views in brief. Row order without `ORDER BY` is not defined. Java example: map `GROUP BY` and a window function to the equivalent Java streams code, so a Java developer sees the semantics (pure JDK). Classic problems belong to `sql-interview-problems.md` (batch 2): give at most three short examples and refer to that page by backticked path.

### DB2 — `02-schema-design-and-normalization.md` (P1)

Keys: superkey, candidate, primary, natural against surrogate, composite, foreign, unique. Functional dependencies, the attribute closure, and how to find candidate keys. The anomalies (insert, update, delete). 1NF, 2NF, 3NF, BCNF with one worked decomposition each; 4NF and 5NF in brief; lossless join and dependency preservation. Denormalization: when and how (summary columns, duplicated columns, materialized views), and the cost (write amplification, consistency work). Constraints (`NOT NULL`, `CHECK`, `UNIQUE`, foreign keys and their `ON DELETE` actions) and why the database, not only the application, must enforce invariants. Relationship modeling (1:1, 1:N, M:N with a junction table), self references, inheritance mappings (single table, class table, concrete table; link `java/16` if it covers JPA inheritance). Common schema problems: entity-attribute-value (EAV), polymorphic associations, JSON columns (PostgreSQL `jsonb`) against normalized columns, soft delete and its effect on unique constraints, audit columns, enums against lookup tables. Data types: `DECIMAL` for money (not floating point), time stamps and time zones (`timestamptz`), text lengths. IDs: link `../hld/fundamentals/15-unique-id-generation.md`. Schema evolution: expand-and-contract migrations, online schema change tools (gh-ost, pt-online-schema-change) in brief, migration tools (Flyway, Liquibase) in brief. A worked interview exercise: design the schema for a small domain (for example an online store with orders, items, and payments), with the reason for each table and key. Java example: compute attribute closures and candidate keys for a set of functional dependencies (pure JDK).

### DB3 — `03-indexing.md` (P1)

Why an index helps (page reads). The B+ tree as an index on disk pages: page size (PostgreSQL 8 KB, InnoDB 16 KB default, from the vendor docs), fanout, the height of a tree for a billion rows (show the calculation), inner pages against leaf pages, linked leaves for range scans, page splits and fill factor. Clustered index (InnoDB: the table is the primary-key B+ tree; a secondary index stores the primary key, so a lookup costs two tree searches) against a heap table (PostgreSQL: the index stores a tuple ID that points into the heap). Hash indexes (PostgreSQL hash index: equality only; InnoDB adaptive hash index). Composite indexes and the leftmost-prefix rule, column order (equality columns first, then the range column), and sort order. Covering indexes and index-only scans (PostgreSQL `INCLUDE` and the visibility map; InnoDB secondary indexes that cover the query). Partial indexes and expression indexes. Unique indexes and constraints. Selectivity and cardinality, and how the planner estimates them from statistics. When an index is not used: a function on the column, a leading-wildcard `LIKE`, an implicit type conversion, low selectivity, an `OR` across columns, a condition that skips the leftmost column, a small table, stale statistics. The write cost of each index. Random keys (UUIDv4) against ordered keys (UUIDv7, sequences): page splits and cache misses (link `../hld/fundamentals/15-unique-id-generation.md`). Other index types in brief: GIN, GiST, BRIN, bitmap index scans; inverted indexes (link `../hld/fundamentals/11-search-and-indexing.md`) and geospatial indexes (link `../hld/fundamentals/18-geospatial-indexing.md`). Building an index on a live table (`CREATE INDEX CONCURRENTLY` in PostgreSQL; online DDL in InnoDB). Use SQLite `EXPLAIN QUERY PLAN` with `sql-result` blocks to show when SQLite uses an index and when it does not. Java example: a small B+ tree that prints its page splits and runs a range scan along the linked leaves (pure JDK). Tree theory is in `../dsa/foundations/05-trees-and-balanced-bsts.md`: link it, do not repeat it.

### DB4 — `04-transactions-and-isolation.md` (P1)

ACID, each property with the mechanism behind it (atomicity: undo or versions; durability: the write-ahead log, with a link to `kb/databases/06-storage-engines.md` as a backticked path; consistency: constraints plus application invariants; isolation: this page). Commit, rollback, savepoints, autocommit. The anomalies, each with a two-session timeline: dirty write, dirty read, non-repeatable read (fuzzy read), phantom read, lost update, read skew, write skew (the on-call doctors example). The SQL standard isolation levels and the anomalies each forbids. What real products do: PostgreSQL (Read Committed is the default; Read Uncommitted behaves as Read Committed; Repeatable Read is snapshot isolation and also prevents phantoms; Serializable is Serializable Snapshot Isolation, which aborts transactions with serialization failures, SQLSTATE 40001), MySQL InnoDB (Repeatable Read is the default; consistent nonlocking reads from a read view; locking reads with record, gap, and next-key locks; how lost updates behave under Repeatable Read), and in brief Oracle (Read Committed default; its Serializable is snapshot isolation). Check each of these against the vendor docs. MVCC: versions, snapshots, visibility rules; PostgreSQL row versions (`xmin`, `xmax`) against InnoDB undo logs (the physical side, VACUUM and purge, belongs to page 06; give two sentences and the backticked path). Locks: shared and exclusive, row and table locks, intention locks, `SELECT ... FOR UPDATE`, `FOR SHARE`, `NOWAIT`, `SKIP LOCKED` (and the job-queue use), two-phase locking (2PL) and strict 2PL. Deadlocks: how the engine detects them (wait-for graph), what the victim sees, lock-order rules, timeouts (`deadlock_timeout` and `lock_timeout` in PostgreSQL, `innodb_lock_wait_timeout` in MySQL). Optimistic locking with a version column against pessimistic locking, with the retry loop. Constraints as concurrency control: unique constraints, the PostgreSQL exclusion constraint for overlapping ranges, conditional `UPDATE ... WHERE stock >= 1` with a row count check. Retrying serialization failures and deadlock victims. Long transactions and their costs. The atomic commit that the transactional outbox relies on (link `../hld/distributed-systems/03-distributed-transactions.md`). Link `../hld/fundamentals/07-consistency-and-cap.md` for the difference between isolation and distributed consistency. Read `../lld/fundamentals/09-concurrency-in-lld.md` (its SQL optimistic-locking example) and `kb/java/19-spring-data-and-transactions.md` (its isolation section) first, and do not contradict them. Java example: an MVCC simulation with snapshot visibility that shows a write skew under snapshot isolation, or a wait-for-graph deadlock detector (pure JDK, deterministic).

### DB5 — `05-query-execution-and-tuning.md` (P1)

The life of a query: parse, rewrite, plan, execute. The cost-based optimizer: statistics (`ANALYZE`, histograms, most-common values), cardinality estimates, cost units, and why a wrong estimate gives a wrong plan. Access methods: sequential scan, index scan, index-only scan, bitmap heap scan. Join algorithms: nested loop, index nested loop, hash join, merge join, each with its cost, its memory need, and when the planner picks it (MySQL has hash joins since 8.0.18: check). Join order. Sorts, `LIMIT`, and top-N. Reading a plan: PostgreSQL `EXPLAIN` and `EXPLAIN (ANALYZE, BUFFERS)` (cost, rows, actual time, loops, the estimate-against-actual check); MySQL `EXPLAIN` (`type` values from `const` to `ALL`, `key`, `rows`, `Extra`: `Using index`, `Using filesort`, `Using temporary`) and `EXPLAIN ANALYZE`; SQLite `EXPLAIN QUERY PLAN` (runnable here). Follow the "PostgreSQL `EXPLAIN ANALYZE`" rule in "SQL rules". The N+1 problem: the theory, why the round trips dominate, how to detect it (statement logs, `pg_stat_statements`, query counts per request, tracing), and the SQL-level fixes (a join, a batch `IN` query); link `kb/java/16-jdbc-jpa-and-hibernate.md` for the JPA causes and fixes. Pagination: `OFFSET` cost against keyset (seek) pagination, with the index it needs (`java/19` points here). A tuning workflow: find the slow query (slow query log, `pg_stat_statements`), read the plan, form a hypothesis, change one thing (an index, a rewrite, fresh statistics), and measure. Rewrites: sargable predicates (define the term), `EXISTS` against `IN`, `UNION ALL` against `UNION`, `SELECT *` costs, avoiding functions on indexed columns. Prepared statements and plan caching (PostgreSQL generic against custom plans). Why a query that the buffer pool serves is still slower than a cache lookup (link `../hld/fundamentals/03-caching.md`). Java example: nested-loop, hash, and sort-merge joins over two in-memory tables that print the comparison counts and the same result rows (pure JDK, deterministic), or a query counter that shows N+1 against one join.
